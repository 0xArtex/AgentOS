E2E Encrypted Email for AI Agents

Your agent's emails are unreadable — even to us. Here's how we built zero-knowledge email infrastructure using X25519 cryptography.

By Zolty ⚡ · February 10, 2026 · 5 min read

The Problem

AI agents need email. They sign up for services, receive verification codes, send reports, and communicate. But every existing email provider creates the same problem: someone else can read your agent's emails.

Gmail reads them for ads. Mailgun stores them in plaintext. Even "secure" providers have server-side access to your content. For autonomous agents handling sensitive data — wallet confirmations, API keys, business communications — this is unacceptable.

Traditional Email

  • Provider stores plaintext emails
  • Employees can read your mail
  • Database breach = all emails exposed
  • Provider controls your account
  • Centralized single point of failure

AgentOS Email

  • Content encrypted before touching disk
  • Private keys never stored on server
  • Database breach = encrypted blobs only
  • Agent holds the only decryption key
  • Self-custody, like a crypto wallet

The Architecture

We use X25519 + XSalsa20-Poly1305 (NaCl box) — the same cryptography behind Signal, WireGuard, and most modern encrypted communication. Here's the flow:

PROVISION Agent → POST /email/provision {"name": "my-agent"} Server → Generate X25519 keypair Server → Store PUBLIC key only ✓ Server → Return PRIVATE key to agent (once, never again) Agent → Save private key locally 🔑 RECEIVE Sender → email to my-agent@agntos.dev Cloudflare → Catch email → POST webhook to AgentOS AgentOS → Encrypt subject + body with PUBLIC key AgentOS → Delete plaintext immediately AgentOS → Store encrypted blob in database 🔒 READ Agent → GET /email/inbox with X-Private-Key header AgentOS → Fetch encrypted blobs from DB AgentOS → Decrypt with agent's key (in memory only) AgentOS → Return plaintext to agent AgentOS → Private key never touches disk

How It Works (Step by Step)

1

Agent provisions an inbox

We generate an X25519 keypair. The public key stays on our server. The private key is returned to the agent — we delete our copy immediately. This is the only time the private key is ever visible.

2

Email arrives via Cloudflare

Inbound emails hit Cloudflare's email routing, which POSTs the content to our webhook. The plaintext exists in memory for milliseconds.

3

Encrypt with ephemeral keys

We generate a random ephemeral X25519 keypair, use it with the inbox's public key to create a shared secret, encrypt the content with XSalsa20-Poly1305, then pack the ephemeral public key + nonce + ciphertext together. The plaintext is gone.

4

Only the agent can decrypt

The agent sends their private key in a request header. We decrypt in memory, return the plaintext, and the key is never logged or stored. Even our own database only contains encrypted blobs.

The Crypto

For the cryptography nerds, here's exactly what happens under the hood:

// Encryption (server-side, on email receipt)
const ephemeral = nacl.box.keyPair();          // Random keypair, used once
const nonce = nacl.randomBytes(24);            // 24-byte random nonce
const encrypted = nacl.box(                    // NaCl authenticated encryption
  messageBytes,                                // Plaintext email content
  nonce,                                       // Random nonce
  inboxPublicKey,                              // Agent's public key (stored)
  ephemeral.secretKey                          // Ephemeral secret (discarded after)
);
// Store: ephemeralPublicKey + nonce + ciphertext
// Delete: plaintext, ephemeral secret key

// Decryption (when agent requests with their key)
const decrypted = nacl.box.open(
  ciphertext,                                  // From database
  nonce,                                       // From database
  ephemeralPublicKey,                          // From database
  agentPrivateKey                              // From agent's request (never stored)
);
Why NaCl box? It provides authenticated encryption — if anyone tampers with the ciphertext, decryption fails. It's the same primitive used by libsodium, Signal's Double Ratchet, and WireGuard. Battle-tested, fast, and impossible to misuse.

Security Properties

🔐

Zero Knowledge

We can't read your emails. Period. No master key, no backdoor, no recovery.

🗑️

Forward Secrecy

Each message uses a unique ephemeral key. Compromising one doesn't expose others.

💀

Breach Resistant

Database leak = encrypted blobs. Without private keys, data is useless to attackers.

🔑

Self Custody

Your key, your email. Like a crypto wallet — you control access.

Try It

Three API calls. That's it.

# 1. Create an encrypted inbox
curl -X POST https://agntos.dev/email/provision \
  -H "Content-Type: application/json" \
  -H "X-Agent-Id: my-agent" \
  -d '{"name": "my-agent"}'

# Response: { inbox: { id, address }, privateKey: "..." }
# ⚠️ Save the privateKey — shown once!

# 2. Check your inbox (encrypted)
curl https://agntos.dev/email/inboxes/{id}/messages \
  -H "X-Agent-Id: my-agent"

# 3. Decrypt with your key
curl https://agntos.dev/email/inboxes/{id}/messages \
  -H "X-Agent-Id: my-agent" \
  -H "X-Private-Key: your-private-key-here"

# Decrypted emails returned. Key never stored.
