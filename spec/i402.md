# i402 — Intent Fulfillment Protocol

**Version:** 0.1 (draft)
**Status:** proposed
**Companion to:** [x402](https://x402.org) — HTTP Payment Required
**Reference implementation:** [AgentOS](https://agntos.dev)
**License:** this specification is released under CC0 / public domain. Implementations may be independently licensed.

---

## Abstract

i402 is an open protocol for translating an agent's natural-language or structured **intent** into an ordered sequence of **x402-settled provider calls** that collectively fulfill that intent. Where x402 answers *"how does an agent pay for a single call,"* i402 answers *"how does an agent accomplish a goal that requires many calls, without knowing in advance which providers, in what order, at what cost."*

An i402 server receives an intent and responds with a **plan**: a validated, priced, schema-bound list of x402 calls. The client (or the server, by delegation) executes the plan. Outcomes become composable across the open web: any provider exposing a compatible capability can appear in any plan, settled in USDC, owned by the calling wallet.

i402 does not specify the orchestrator's reasoning, the set of capabilities, or the choice of underlying payment rail. It specifies only the wire format, the session semantics, and the minimum guarantees every conforming server and client must uphold.

---

## 1. Motivation

### 1.1 The fragmentation problem

As autonomous agents proliferate, the number of callable services available to them grows faster than any single agent can track. A typical goal — *"launch a small product,"* *"research this topic,"* *"grow an audience"* — requires orchestrating five to twenty services, from search APIs to infrastructure providers to social posting endpoints. Today, each agent developer must:

1. Know every relevant service exists.
2. Know which combination solves the goal.
3. Compare price, latency, and reliability across them.
4. Glue them in the correct order.
5. Pay each separately.

This is the **fragmentation tax**. It does not decrease with more services; it increases. A language model handed fifteen tools outperforms the same model handed three thousand tools. Flat capability lists make agents worse, not better.

### 1.2 Why x402 alone is insufficient

x402 standardizes payment for a single provider call. It does not help an agent decide which calls to make. Without a layer above, every agent re-derives the composition problem from scratch on every goal — the same agent may solve it differently on different days, and different agents solve it non-interoperably. x402 is a necessary but incomplete foundation.

### 1.3 i402's proposed answer

i402 adds one HTTP-level semantic: when a server receives a request it cannot fulfill directly, it may respond with a structured **plan** — a composed list of x402 calls that *would* fulfill the request if executed. The client inspects the plan, optionally approves it, and executes it (or hands execution back to the server).

This turns any server into a potential **orchestrator** for its domain. AgentOS implements a general-purpose orchestrator; specialized orchestrators (travel, DeFi, creative, e-commerce) can implement the same protocol for their niches. Agents interact with all of them through identical HTTP semantics.

## 2. Relationship to x402

i402 and x402 are **siblings**, not alternatives. They compose:

| Protocol | Answers |
|----------|---------|
| x402 | *"How does a client pay for this one call?"* |
| i402 | *"What is the composed set of calls that fulfills this intent?"* |

Every step in an i402 plan is an x402 call. Every x402 endpoint is a potential step in some i402 plan. An i402 server may itself be an x402 endpoint (charging an **orchestration fee** separately from the steps), and an x402 endpoint may expose i402 semantics on specific routes.

Implementations MAY support only one of the two, but a complete agent-facing server SHOULD support both.

## 3. Terminology

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY**, and **OPTIONAL** are to be interpreted as described in [RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119).

- **Agent**: an autonomous software actor with a wallet identity, initiating i402 requests to accomplish goals.
- **Client**: the runtime making the HTTP request. May be the agent directly or a framework on its behalf.
- **Intent**: the agent's goal, expressed in natural language, structured form, or a mixture.
- **i402 server** (*"orchestrator"*): an HTTP server that receives intents and returns plans.
- **Plan**: a structured, schema-bound list of ordered steps that together fulfill an intent.
- **Step**: a single x402 call within a plan. Each step has a provider, a capability, an input, a schema-bound output, and a USDC cost.
- **Provider**: an x402-compatible endpoint registered with an i402 server as callable within a capability class.
- **Capability class**: a canonical interface (named input/output schemas) that multiple providers can implement interchangeably.
- **Session**: a persistent, multi-turn conversation between an agent and an i402 server, maintaining goal state across messages.
- **Orchestration fee**: a USDC amount an i402 server charges for generating and optionally executing a plan, separate from step costs.
- **Escrow**: USDC deposited by the agent that the server draws against as steps complete successfully.

## 4. Protocol Overview

```
   Agent                       i402 Server                     x402 Providers
     │                              │                                │
     │  POST /chat { intent, budget } ──►                             │
     │                              │                                │
     │                              │  [plan generation]             │
     │                              │                                │
     │  ◄── 402 with body {plan_id, steps, total_cost} ───            │
     │                              │                                │
     │  [inspect, approve]          │                                │
     │                              │                                │
     │  POST /chat (approve)  ─►    │                                │
     │                              │                                │
     │                              │  POST step[0]  ──►             │
     │                              │  ◄──  step[0] result           │
     │                              │  POST step[1]  ──►             │
     │                              │  ◄──  step[1] result           │
     │                              │  ...                           │
     │                              │                                │
     │  ◄── 200 { session, spent, artifacts } ─                      │
     │                              │                                │
```

Minimum viable flow:

1. Client POSTs to an i402 endpoint with an intent and a budget.
2. Server generates a plan of x402 calls that fulfill the intent.
3. Server responds with HTTP `402` carrying the plan in a structured body.
4. Client either approves the plan (continues in the same session) or walks away.
5. Once approved, steps execute in order. Each step's cost is debited from the agent's escrow as the step completes successfully.
6. On completion, server returns a final summary including artifacts produced and USDC spent.

## 5. Request Format

### 5.1 Endpoint

An i402 server MUST expose at least one endpoint that accepts intents. The canonical endpoint is:

```
POST /chat
```

Servers MAY expose additional domain-specific endpoints (e.g., `/launch-product`, `/research`) that accept narrower intents; the response format is identical.

### 5.2 Request headers

- `Authorization: Bearer <token>` — OPTIONAL agent identity token (server-issued or wallet-signed JWT).
- `X-Wallet-Address: <address>` — OPTIONAL canonical wallet identity if no bearer token.
- `X-Session-Id: <session_id>` — OPTIONAL. If omitted, a new session is created. If present, the request continues an existing session.
- `X-Payment-Signature: <signature>` — OPTIONAL x402 payment signature covering the orchestration fee. REQUIRED if the server's plan generation is paid (most public servers).
- `Content-Type: application/json` — REQUIRED.

### 5.3 Request body

```jsonc
{
  "intent": "Launch a product reselling sneakers to teenagers.",
  "params": { "target_audience": "teens", "region": "US" },   // OPTIONAL structured parameters
  "budget_usdc": 50.00,                                        // MUST be >= orchestration fee
  "deadline_seconds": 1800,                                    // OPTIONAL; server MAY refuse if too tight
  "quality": "best",                                           // OPTIONAL; "fast" | "cheap" | "best"
  "constraints": {                                             // OPTIONAL
    "exclude_capabilities": ["social_post"],
    "exclude_providers": ["some.provider.id"],
    "require_providers": ["agentos.domain_register"]
  },
  "approve": false,                                            // OPTIONAL; if true, execute immediately without returning plan for review
  "auto_approve_under_usdc": 5.00                              // OPTIONAL; auto-execute if plan cost <= this
}
```

Fields:

- **`intent`** (string, REQUIRED): the agent's goal. Servers MAY accept natural-language or a structured tag drawn from their published capability vocabulary.
- **`params`** (object, OPTIONAL): structured parameters supplementing the intent.
- **`budget_usdc`** (number, REQUIRED): maximum the agent authorizes for this request. Servers MUST NOT spend more than this without a new approval.
- **`deadline_seconds`** (number, OPTIONAL): how long the agent is willing to wait. Servers MAY refuse the request if the deadline is impossible.
- **`quality`** (enum, OPTIONAL): routing hint. `"fast"` prioritizes latency; `"cheap"` prioritizes cost; `"best"` prioritizes reputation. Default: `"best"`.
- **`constraints`** (object, OPTIONAL): exclusions and requirements on the plan.
- **`approve`** (bool, OPTIONAL): if `true`, the server skips the 402 plan-review step and executes immediately (trusting the client to have authorized the full budget).
- **`auto_approve_under_usdc`** (number, OPTIONAL): if the generated plan costs less than this, execute without 402 round-trip.

## 6. Response Format — the i402 Plan

### 6.1 The 402 plan response

When a server cannot fulfill the intent directly but has generated a plan, it MUST respond with HTTP `402 Payment Required` and a JSON body matching the **plan schema** below. This is the core of i402.

```
HTTP/1.1 402 Payment Required
Content-Type: application/json
X-i402-Version: 0.1
```

```jsonc
{
  "session_id": "sess_8f3a2b1c",
  "plan_id": "plan_7e9d1234",
  "status": "awaiting_approval",
  "intent": {
    "original": "Launch a product reselling sneakers to teenagers.",
    "interpreted": "End-to-end launch: market research, branding, domain, landing page, social presence, email."
  },
  "steps": [
    {
      "step_id": "s1",
      "capability": "web_search",
      "provider": "exa.web_search",
      "description": "Research sneaker resale market for teen demographic",
      "input": { "query": "sneaker resale trends teenagers 2026", "max_results": 10 },
      "input_schema": { "$ref": "https://i402.agntos.dev/schemas/web_search.input.json" },
      "output_schema": { "$ref": "https://i402.agntos.dev/schemas/web_search.output.json" },
      "cost_usdc": 0.10,
      "eta_seconds": 4,
      "x402": {
        "endpoint": "https://api.exa.ai/search",
        "method": "POST",
        "payment_rail": "x402-base"
      }
    },
    {
      "step_id": "s2",
      "capability": "register_domain",
      "provider": "agentos.domain_register",
      "description": "Register the chosen product domain",
      "input": { "domain_preferences": ["freshkicks.io", "hypefeet.co"], "years": 1 },
      "input_schema": { "$ref": "https://i402.agntos.dev/schemas/register_domain.input.json" },
      "output_schema": { "$ref": "https://i402.agntos.dev/schemas/register_domain.output.json" },
      "cost_usdc": 9.99,
      "eta_seconds": 30,
      "x402": {
        "endpoint": "https://agntos.dev/domain/register",
        "method": "POST",
        "payment_rail": "x402-solana"
      },
      "depends_on": ["s1"]
    }
    // ...additional steps
  ],
  "totals": {
    "step_cost_usdc": 34.59,
    "orchestration_fee_usdc": 0.50,
    "total_cost_usdc": 35.09,
    "within_budget": true,
    "eta_seconds": 240
  },
  "approval": {
    "required": true,
    "expires_at": "2026-04-22T18:42:00Z",
    "approve_url": "https://agntos.dev/chat",
    "approve_method": "POST",
    "approve_body": { "session_id": "sess_8f3a2b1c", "plan_id": "plan_7e9d1234", "approve": true }
  }
}
```

### 6.2 Required fields

Every plan response MUST include:

- `session_id` — the session this plan belongs to.
- `plan_id` — unique identifier for this plan within the session.
- `status` — one of `"awaiting_approval"`, `"approved"`, `"executing"`, `"completed"`, `"failed"`, `"budget_exceeded"`, `"clarification_needed"`.
- `intent.original` — the client's verbatim intent.
- `steps` — an array of zero or more steps, each matching the **step schema** in §6.3.
- `totals.step_cost_usdc` — sum of all step costs.
- `totals.orchestration_fee_usdc` — the server's fee for generating (and optionally executing) the plan.
- `totals.total_cost_usdc` — sum of step costs + orchestration fee.
- `totals.within_budget` — boolean; false if the plan exceeds the client's submitted budget.

### 6.3 Step schema

Every step MUST include:

- `step_id` — unique within the plan.
- `capability` — a canonical capability class name (§9).
- `provider` — provider identifier known to the server.
- `input` — concrete parameters conforming to the capability's input schema.
- `cost_usdc` — non-negative USDC amount.
- `x402` — object describing how the step is called: `endpoint`, `method`, `payment_rail`.

A step SHOULD include:

- `description` — human-readable summary for display to operators.
- `input_schema`, `output_schema` — URIs or inline JSON Schema documents.
- `eta_seconds` — estimated latency.
- `depends_on` — array of prior `step_id`s whose output must be available before this step runs.

### 6.4 Clarification responses

If the server determines the intent is too ambiguous to plan safely, it MAY respond `402` with status `"clarification_needed"` and a `questions` field listing what it needs:

```jsonc
{
  "session_id": "sess_abc",
  "status": "clarification_needed",
  "questions": [
    { "id": "q1", "text": "What region are you targeting?" },
    { "id": "q2", "text": "Is this DTC or wholesale?" }
  ]
}
```

The client answers by POSTing back to the same endpoint with the same `session_id` and an `answers` object.

### 6.5 Direct-fulfillment responses

A server MAY respond with HTTP `200` and a standard x402 result if it can fulfill the intent directly without composing multiple providers. i402 semantics apply only when composition is needed.

## 7. Plan Execution

### 7.1 Execution modes

Three execution modes are defined. A plan response MUST declare which the server supports via `totals.execution_modes`.

- **`agent_side`**: the server returns the plan; the client executes each step itself. Each step's output is returned to the client, which passes it as input to the next step. Transparent but context-heavy on the client side.
- **`server_side`**: the server executes the full plan and streams results. The client pays the total upfront (escrow) and receives a stream of step-by-step results. Lower client context cost.
- **`hybrid`**: the client executes simple terminal steps while delegating complex internal steps to the server. Servers MAY recommend a split; clients MAY override.

The execution mode is selected by the client on approval:

```
POST /chat
{ "session_id": "...", "plan_id": "...", "approve": true, "execution": "server_side" }
```

### 7.2 Server-side execution semantics

When execution is `server_side`, the server MUST:

1. Verify the agent has paid (via x402) at least `totals.total_cost_usdc` into escrow.
2. Stream responses via `text/event-stream` (Server-Sent Events) or HTTP chunked transfer.
3. Emit events in the order defined in §7.3.
4. Debit escrow by each step's actual cost (not estimated) only after the step returns successfully.
5. Refund remaining escrow to the agent's wallet on completion or cancellation.

### 7.3 Event stream format

Each event is a single line prefixed with `event: <name>\ndata: <json>\n\n`.

Defined events:

- `session` — emitted once at start. `{ "session_id": "..." }`
- `plan` — emitted after plan generation. `{ "plan_id": "...", "steps": [...], "total_cost_usdc": N }`
- `step_start` — emitted when a step begins. `{ "step_id": "...", "provider": "...", "cost_usdc": N }`
- `step_result` — emitted on step success. `{ "step_id": "...", "output": {...}, "latency_ms": N, "cost_charged_usdc": N }`
- `step_error` — emitted on step failure. `{ "step_id": "...", "error": "...", "retry_with": "<next provider>" | null }`
- `clarification_needed` — emitted mid-execution if the server needs input. `{ "questions": [...] }`
- `summary` — emitted at end. `{ "spent_usdc": N, "remaining_escrow_usdc": N, "artifacts": [...], "status": "completed" | "failed" | "cancelled" }`

### 7.4 Agent-side execution

Under `agent_side`, the server returns the plan and stops. The client:

1. For each step in order, POSTs to `step.x402.endpoint` with `step.input` and appropriate x402 payment headers.
2. Collects the output.
3. Passes relevant output fields into the next step's input (resolving `depends_on`).

The client MAY report back to the i402 server at `POST /chat/{session_id}/step-result` for bookkeeping, but this is OPTIONAL.

## 8. Session Model

### 8.1 Purpose

Sessions enable **multi-turn orchestration** — the agent can continue a conversation across several messages, with each new message inheriting all prior context (past plans, past artifacts, cumulative spend, established constraints).

### 8.2 Session lifecycle

- Created on first `/chat` request without `X-Session-Id`.
- Identified by a server-generated `session_id` returned in the first response.
- Clients SHOULD include `X-Session-Id` on all subsequent requests in the same logical conversation.
- Sessions are PER-WALLET — only the originating wallet may continue the session.
- Sessions have an idle timeout (server policy; AgentOS default: 24h). Expired sessions cannot be resumed and remaining escrow is refunded.

### 8.3 Session state

A server maintains per-session:

- The goal graph (structured history of what the agent has asked for)
- All prior plans and their execution results
- Artifacts produced (domains owned, VPSes deployed, accounts, files)
- Cumulative USDC spent against the session budget
- A rolling context summary used for LLM prompt caching

### 8.4 Follow-up semantics

When a new message arrives in an existing session, the server SHOULD:

1. Interpret the new message in the context of prior artifacts. ("Now do marketing" refers to the product already established.)
2. Generate a plan that operates on existing artifacts rather than duplicating them.
3. Reuse already-chosen providers where possible (brand voice consistency).
4. Emit a new `plan` event for just the additional steps.

### 8.5 Session endpoints

```
GET  /chat/{session_id}         — full session state
GET  /chat/{session_id}/spend   — running cost breakdown
POST /chat/{session_id}/cancel  — halt execution, refund remaining escrow
DELETE /chat/{session_id}       — archive session, refund escrow
```

## 9. Capability Classes

### 9.1 Purpose

Capability classes are the canonical interfaces that let providers be **drop-in replaceable**. Two providers sharing a capability class share input and output schemas, so an orchestrator can swap between them based on price, latency, or reputation without the client caring.

### 9.2 The capability vocabulary

i402 does not mandate a fixed vocabulary. Servers publish their supported capabilities at:

```
GET /chat/capabilities
Response:
{
  "version": "0.1",
  "capabilities": [
    { "name": "web_search", "input_schema": {...}, "output_schema": {...} },
    { "name": "register_domain", "input_schema": {...}, "output_schema": {...} },
    ...
  ]
}
```

The i402 **canonical capability set** (maintained at https://i402.agntos.dev/capabilities) is a non-normative reference. Servers SHOULD prefer canonical names when a suitable one exists, and SHOULD contribute new capability proposals to the canonical set when they introduce widely useful ones.

### 9.3 Canonical capabilities (v0.1 draft)

```
web_search, web_scrape, summarize, translate, embed,
image_gen, image_edit, video_gen, tts, stt,
send_sms, send_email, voice_call, provision_phone, provision_email_inbox,
deploy_vps, register_domain, dns_manage,
social_post, social_account_provision,
code_exec, file_store,
research_report, launch_product, grow_audience          // compound capabilities (§9.4)
```

### 9.4 Compound capabilities

Some capabilities are inherently composite — `launch_product` expands into research + domain + landing page + social + email. These are supported as **first-class capabilities** whose steps are themselves other capabilities. A server implementing `launch_product` generates a plan whose steps are drawn from simpler capabilities.

Compound capabilities are how orchestrator servers express their domain expertise. A travel-specialized i402 server would publish `book_trip`; a DeFi server would publish `yield_farm`.

### 9.5 Schemas

Each capability class MUST define:

- A JSON Schema for the input.
- A JSON Schema for the output.
- Optional semantic hints (e.g., units for numeric fields, example values).

All schemas are versioned. Breaking changes require a new capability name (`web_search` → `web_search_v2`).

## 10. Provider Registration & Discovery

### 10.1 Server-side registry

i402 servers maintain a provider registry — a list of x402-compatible endpoints they know about, each tagged with one or more capability classes. Entries MUST include:

- Stable provider ID.
- Capability class(es).
- Endpoint URL and HTTP method.
- Expected x402 payment rail (Solana or EVM).
- Canonical cost per call in USDC.
- Typical p50 and p99 latency.
- Observed success rate (rolling window).
- Reputation score.
- Input/output schemas (or references to them).

### 10.2 Provider sources

A server MAY populate its registry from:

- **First-party services** it directly operates (e.g., AgentOS's phone/email/VPS primitives).
- **Federated marketplaces** such as Coinbase's Agentic Market, queried via their catalog APIs.
- **Skill catalogs** such as ClawHub (long-tail services).
- **Agent-submitted providers** (subject to reputation filtering; see §12 for security).
- **Manual curation.**

### 10.3 Public discovery endpoint

Servers SHOULD expose:

```
GET /providers?capability=<name>
```

Returning a list of providers for that capability, with their current cost, latency, and reputation. Agents MAY use this to inspect the registry before submitting intents, though this is not required for normal use.

## 11. Payment & Escrow

### 11.1 Relationship to x402

All monetary settlement is x402. i402 adds no new payment mechanism. Specifically:

- The orchestration fee is collected as a standard x402 payment on the `/chat` endpoint.
- Each step in a plan is settled via the step's own x402 call.

### 11.2 Server-side execution requires escrow

When executing server-side, the server must be able to pay providers on the agent's behalf. Two patterns are permitted:

- **Pre-funded escrow.** Agent pays `total_cost_usdc` upfront (x402 call). The server holds this balance against the agent's wallet and debits per step. Unused escrow is refunded at session close.
- **Just-in-time settlement.** Server executes step N only after the agent signs a new x402 payment for exactly step N's cost. Requires more round-trips but no trust in the server's escrow.

Pre-funded escrow is the default; just-in-time is RECOMMENDED for high-value or low-trust scenarios.

### 11.3 Refund semantics

- A step that fails MUST NOT charge the agent.
- A cancelled session MUST refund unspent escrow within one block confirmation.
- If the server cannot refund (e.g., treasury compromise), the agent MAY file a dispute via the server's published dispute URL. Dispute resolution is out of scope for this spec.

### 11.4 Orchestration fee

Servers MAY charge a flat fee, a percentage of step costs, or a blend. The fee MUST be disclosed in the plan's `totals.orchestration_fee_usdc`. Agents can reject plans with fees they consider excessive before approval.

## 12. Error Codes & Failure Modes

### 12.1 HTTP status codes

- **200 OK** — the server fulfilled the intent directly without multi-step composition.
- **202 Accepted** — server is executing a server-side plan; check `/chat/{session_id}` for status.
- **402 Payment Required** — server has a plan requiring approval and payment. **Primary i402 response.**
- **400 Bad Request** — malformed intent, budget missing, invalid schema.
- **402 Payment Required with `status: "budget_exceeded"`** — the cheapest possible plan exceeds the agent's budget.
- **402 Payment Required with `status: "clarification_needed"`** — intent too ambiguous.
- **403 Forbidden** — the wallet lacks permission (e.g., session belongs to another wallet).
- **404 Not Found** — no matching capability or provider available.
- **410 Gone** — session or plan has expired.
- **429 Too Many Requests** — rate limit.
- **500 Internal Server Error** — orchestrator crashed; agent SHOULD retry with a fresh session.
- **503 Service Unavailable** — server temporarily overloaded; include `Retry-After` header.

### 12.2 Structured error body

All non-2xx responses SHOULD return a structured body:

```jsonc
{
  "error": "budget_exceeded",
  "message": "Cheapest viable plan costs $8.20; budget was $5.00.",
  "cheapest_plan_cost_usdc": 8.20,
  "hint": "Raise budget_usdc or add constraints.exclude_capabilities to reduce scope."
}
```

### 12.3 Mid-execution failures

During server-side execution, individual step failures are reported via `step_error` events (§7.3). The server's recovery policy — retry same provider, fall back to next-ranked, or abort — is governed by the `quality` hint and the capability's criticality.

## 13. Security Considerations

### 13.1 Replay protection

Each plan approval MUST be tied to a specific `plan_id`. Servers MUST reject approval attempts for plans that have already been executed or cancelled.

### 13.2 Escrow integrity

Servers holding escrow are custodians. Reference implementations SHOULD use non-custodial escrow patterns (multisig, smart-contract escrow on Base/Solana) where available. Purely custodial escrow is permitted but increases trust requirements on the server.

### 13.3 Provider spoofing

An i402 server MUST NOT silently redirect a step's payment to a different wallet than the one registered for the provider. Clients SHOULD inspect `step.x402.endpoint` and the resolved treasury address before approving server-side execution.

### 13.4 Intent injection

An agent's natural-language intent passes through the server's LLM. Servers MUST sandbox intent text: it is never eval'd, never used as code, never passed to shell contexts. LLM prompt-injection attacks on the orchestrator's system prompt are the server's responsibility to mitigate.

### 13.5 Wallet binding

Sessions are bound to the creating wallet. A plan approved by wallet A cannot be executed against escrow from wallet B. The server MUST verify wallet identity on every privileged endpoint via either (a) a valid bearer token issued to that wallet, or (b) a fresh x402 payment from that wallet.

### 13.6 Provider output validation

v0.1 of this spec does NOT require servers to validate provider outputs against declared schemas. A malicious or buggy provider could return malformed data that propagates through the plan. Clients SHOULD treat step outputs as untrusted. Future spec versions MAY mandate schema validation with reputation slashing on malformed output.

### 13.7 Cost oracle attacks

Declared `cost_usdc` is based on the server's current view of provider pricing. A provider that changes its x402 price between plan generation and execution could cause a step to revert for insufficient payment. Servers SHOULD refresh quotes if a plan is executed more than 5 minutes after generation.

## 14. Extensibility & Versioning

### 14.1 Version header

All i402 responses MUST include `X-i402-Version: <major.minor>`. Clients SHOULD check this and degrade gracefully on unknown versions.

### 14.2 Backwards compatibility

Within a major version, additions to the plan schema MUST be non-breaking. New fields are OPTIONAL. Deprecated fields remain functional for at least two minor versions.

### 14.3 Custom extensions

Servers MAY include `x-*` prefixed fields at any level of the plan schema for implementation-specific data. Clients SHOULD ignore unknown `x-*` fields rather than rejecting the response.

### 14.4 Capability evolution

Adding a new canonical capability is a minor-version change. Changing the schema of an existing capability is a breaking change requiring a new capability name (`web_search_v2`).

- **Server:** https://github.com/0xArtex/AgentOS (routes under `src/routes/agent-chat.ts`, services under `src/services/i402-*.ts`)
- **Client SDK:** `@agntos/agentos` npm package, `i402` module.
- **CLI:** `agentos chat "<intent>" --budget <N>` using the reference server.

The reference implementation covers:

- General-purpose orchestrator with LLM-driven plan generation (Claude Opus 4.7 + Haiku 4.5 tiering).
- Federated provider registry: AgentOS primitives + Agentic Market + curated externals.
- Full session model with multi-turn continuity.
- Both server-side and agent-side execution modes.
- x402 escrow on Solana and Base.

Other implementations (specialized orchestrators for specific domains) are welcomed and should be listed at https://i402.agntos.dev/implementations.

## 18. Appendix: Non-normative design notes

- **Why 402, not a custom status code?** HTTP 402 is reserved for payment-related semantics and has historically been underused. Using 402 for both x402 and i402 keeps both protocols within one reserved slot, and aligns with the real semantic — the server is telling the client "I need you to authorize some payments before I can do this."
- **Why not gRPC or WebSocket?** REST + SSE is the lowest-friction, most-portable transport for open agent infrastructure. Future versions MAY specify gRPC or WebSocket bindings.
- **Why allow both server-side and agent-side execution?** Different agent runtimes have different constraints. A lightweight agent in a browser benefits from server-side; a sophisticated orchestration-aware agent may prefer agent-side for full visibility.
